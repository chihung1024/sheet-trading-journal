# Gate D / D1a — Reproducibility & Provenance Architecture Audit

Date: **2026-08-09**

## Mandate

Audit the current calculation, serialization, market-data and test boundaries before implementing a calculation manifest or deterministic replay mechanism.

This is an **evidence/proposal** Batch. It does not authorize runtime changes, D1 schema changes, Worker API changes, provider abstraction, Schema 3, broker-execution redesign, futures/derivatives support, or note-derived chronology.

Reviewed baseline:

- repository `chihung1024/sheet-trading-journal`
- protected main `41338e598f027a502a81c7d08eaec3c2f4069a04`
- D1 schema 2
- Gate-D-start recovery `backup-gate-d-start-41338e5`

---

# Executive finding

The project already contains enough compatible boundaries to implement Gate D **without a database or Worker contract migration**.

The preferred path is:

1. introduce pure/versioned canonicalization + hashing contracts first;
2. reuse current market/FX/synthetic valuation state rather than abstract providers;
3. evolve the existing offline golden fixture into a real deterministic replay;
4. introduce one explicit calculation-as-of/clock seam before claiming replay determinism;
5. only after those contracts pass, attach a small optional `calculation_manifest` to `PortfolioSnapshot` and let the existing opaque snapshot JSON persistence carry it.

The largest current reproducibility gaps are not missing storage. They are:

- no canonical transaction/content hash;
- no calculation-engine SHA in Python snapshots;
- no complete persisted identity for effective market/FX inputs;
- realtime overlay/source-selection metadata is mostly lost after calculation;
- wall-clock state (`datetime.now()`, market stage, today/realtime selection) can change outputs;
- the existing golden fixture asserts only three rounded summary values.

# 1. Snapshot / serialization / storage boundary

## Facts

`PortfolioSnapshot` is the authoritative calculated object uploaded by the Python runner. It contains:

- `updated_at`, `base_currency`, `exchange_rate`;
- optional `benchmark_symbol`;
- root `summary`, `holdings`, `history`, `pending_dividends`;
- `groups`, each with its own summary/holdings/history/pending dividends plus `day_ledger`, `lot_ledger`, and `anomalies`.

The existing optional `benchmark_symbol` is an important compatibility precedent: old snapshots remain valid when the field is absent, while new snapshots publish additional provenance.

`CloudflareClient.upload_portfolio()` serializes `snapshot.model_dump()` inside:

`{target_user_id, data}`

and POSTs it to `/api/portfolio`.

The Worker treats `data` as an opaque JSON object, enforces the 1 MiB payload boundary, stores `JSON.stringify(data)` in `portfolio_snapshots.json_data`, and retains the latest ten snapshots per user. D1 `portfolio_snapshots` contains only `id`, `user_id`, `json_data`, and `created_at`.

The Worker does not validate a nested fixed portfolio schema before storage. The frontend already consumes additive snapshot provenance (`benchmark_symbol`) by reading only fields it understands.

## D1a conclusion

**Do not create a new D1 table or Worker API merely to store the Gate-D manifest.**

The lowest-risk production boundary is an **optional, versioned `calculation_manifest` field on `PortfolioSnapshot`**, added only in D1e after contract tests prove backward compatibility.

The manifest must remain small and content-addressed. Frozen market/FX input rows belong in repository replay fixtures, not production snapshot JSON.

# 2. Authoritative outputs for deterministic replay

## Facts

Current authoritative post-run state is the snapshot **after** canonical Daily-P&L reconciliation and before upload.

Important output contracts already exposed by models/tests include:

- portfolio/group summary values;
- holdings and cost/P&L fields;
- history and linked TWR reliability metadata;
- XIRR numeric compatibility value plus `status`, `reason`, `asof_date`, and conventional-cashflow flag;
- pending dividend records;
- canonical Daily-P&L summary and per-symbol `day_ledger` generated by `daily_pnl_reconciler.py`.

`day_ledger` is actively populated after successful reconciliation. `lot_ledger`, by contrast, is currently model/export scaffolding; no production assignment was found. The existing golden test only asserts that it is list-shaped.

## D1a conclusion

D1d golden replay should assert current authoritative outputs, including:

- normalized input transaction projection;
- summary: value/capital/P&L/realized P&L;
- TWR numeric + reliability metadata;
- XIRR numeric + provenance/reliability metadata;
- benchmark TWR/identity where applicable;
- holdings;
- pending dividends;
- history values materially consumed/published by the engine;
- canonical Daily-P&L total/breakdown and `day_ledger`;
- manifest hashes.

**Do not make populated `lot_ledger` a Gate-D requirement.** That would silently expand scope into canonical lot-ledger architecture.

# 3. Transaction input identity

## Facts

`main.prepare_transactions()` is the production normalization boundary. It:

- validates the records API payload;
- maps `txn_date/symbol/txn_type/qty/price/fee/tax/tag` to calculator columns;
- normalizes date/numeric/symbol/type values;
- validates supported types and domain ranges;
- stable-sorts by `Date`, then record `id` when present.

The per-user `raw_user_df` used by C6a is then copied into `PortfolioCalculator`.

No SHA-256/canonical input-hash contract currently exists in the Python calculation path.

Financially/materially relevant normalized source fields are:

- `id` — deterministic persisted validity/FIFO tie-breaker;
- `Date`;
- `Symbol`;
- `Type`;
- `Qty`;
- `Price`;
- `Commission`;
- `Tax`;
- `Tag` — affects group membership.

`note`, `created_at`, and free-form broker metadata are not calculation inputs and must not enter the calculation content hash. User identity is an ownership/scope attribute, not required inside the financial content hash.

Record count and max record id are useful diagnostics but are insufficient to identify content.

## Proposed D1b canonicalization

Version the transaction canonicalization contract independently of the manifest version.

Recommended canonical rows:

- fixed field order;
- stable `Date -> id` row order;
- dates serialized as `YYYY-MM-DD`;
- normalized Symbol/Type exactly as calculation receives them;
- Tag serialized exactly as the normalized calculator input sees it;
- ids as integers;
- finite Python floating values serialized with an exact versioned representation such as `float.hex()` before canonical JSON hashing.

Hash canonical UTF-8 JSON using SHA-256.

Tests must prove:

- repeat invocation produces the same digest;
- irrelevant DataFrame column order does not change it;
- free-form note/created_at changes do not change it;
- any material transaction field/id/order change does change it;
- non-finite or ambiguous canonical inputs fail closed.

# 4. Engine and configuration identity

## Facts

The normal Actions calculation runs under Python 3.10 and pinned `requirements.txt`. The dependency lock includes pinned versions of requests, pandas, numpy, yfinance, pydantic and pyxirr.

Python snapshots currently do not publish the Git commit that produced them.

However, the repository already has a proven pattern: the Gate-C audit uses `GITHUB_SHA` as `source_commit` in machine-readable evidence. GitHub Actions supplies that environment to the runner process.

Runtime values that materially affect calculation include at least:

- resolved per-user benchmark;
- base currency;
- calculator oversell policy/current policy contract;
- calculation as-of/clock context once made explicit.

Many other policies are source-controlled constants and are already transitively identified by engine SHA. They should not all be duplicated in config identity unless independently variable at runtime.

## D1a conclusion

D1b should separate:

- **engine identity**: validated Git source commit;
- **runtime config identity**: canonical versioned object containing only independently variable material settings;
- optional diagnostic dependency-lock hash if later evidence shows value.

A production manifest must reject an empty/ambiguous engine source commit rather than silently call it reproducible.

# 5. Market / FX / split / dividend / synthetic provenance

## Facts — effective calculation state

`MarketDataClient` downloads Yahoo/yfinance data and exposes the actual in-memory calculation state through:

- `market_data[symbol]`;
- historical `fx_rates_by_currency`;
- realtime `realtime_fx_rates_by_currency`;
- compatibility USD/TWD `fx_rates` and `realtime_fx_rate`.

The calculator's material market fields are principally:

- `Close_Adjusted` for valuation;
- `Dividends`;
- `Split_Factor`;
- date index;
- currency-aware historical/realtime FX values.

`AutoPriceSelector` already produces `price_source` and `selection_reason`, but current `MarketDataClient` only logs/prints that metadata and does not retain it as a structured calculation artifact.

Realtime symbol quotes can overwrite the last historical row. That effective numeric value is retained in `market_data`, but the fact/source of the realtime override is not currently persisted as structured provenance.

## Facts — synthetic valuation rows

`transaction_calendar.py` already provides a strong provenance contract for inserted transaction valuation dates:

- `Valuation_Source`;
- `Valuation_Source_Date`;
- normal downloaded rows can be labelled `market`;
- carried rows use `asof_carry_forward`;
- leading seeded rows use `transaction_price_seed`.

This must be reused, not replaced.

## Proposed D1c boundary

Do **not** hash entire vendor DataFrames with irrelevant OHLC/Volume columns.

Create a versioned **effective calculation-input digest** over only fields that can affect the current engine:

For each required symbol, sorted by symbol/date:

- date;
- `Close_Adjusted`;
- `Dividends`;
- `Split_Factor`;
- effective valuation provenance (`Valuation_Source`, `Valuation_Source_Date`), treating absent normal provenance as effective `market` where unambiguous.

For each required currency, sorted by currency/date:

- historical TWD/native FX series actually available to the calculation;
- realtime effective FX value when the calculation context can use it.

Also publish small diagnostics such as:

- symbols/currencies covered;
- market row count;
- FX row count;
- synthetic row counts by source;
- realtime-overlay count/source state once structured tracking is implemented.

Provider/source metadata is valuable evidence but must be separate from the effective numeric input digest. Gate D therefore does **not** require a provider abstraction before reproducibility can be established.

# 6. Wall-clock / realtime nondeterminism

## Facts

`PortfolioCalculator` currently calls wall clock (`datetime.now()` / Taipei current time) to produce or influence:

- snapshot `updated_at`;
- calculation end/current date;
- market-stage metadata;
- whether today's effective asset/FX path uses realtime values.

Therefore frozen transactions + frozen DataFrames alone do **not** define a deterministic replay contract.

## D1a decision

A true D1d replay requires one explicit calculation context/as-of seam.

Recommended contract:

- `calculation_as_of`: material deterministic input controlling date/today/realtime semantics;
- `calculated_at`: run-instance metadata, excluded from deterministic input identity;
- production defaults may resolve from current Taipei time at the runner boundary;
- offline golden replay must inject a fixed as-of/clock.

Do not rely on widespread test monkeypatches of `datetime.now()` as the long-term contract. The seam should be narrow and explicit.

# 7. Existing golden / offline test infrastructure

## Facts

The repository already contains:

`tests/fixtures/golden_case_mixed_tw_us.json`

with:

- fixed market rows for SPY, 2330.TW and NVDA;
- fixed FX;
- transactions;
- dividend rows;
- three expected summary outputs.

`tests/test_daily_pnl.py` provides an offline `FakeMarketDataClient` and `test_golden_snapshot_regression_matrix()`.

Current golden assertions cover only rounded:

- total value;
- realized P&L;
- Daily P&L.

They do not freeze a calculation clock or assert TWR/XIRR/provenance/hash/full canonical outputs.

`tests/test_market_data_pure_invariants.py` is explicitly network-free and already exercises FX normalization/crosses, realtime quote logic, price selection, split factors, dividend policies and market-data invariants.

`tests/test_performance_metrics.py` already gives explicit machine-readable TWR/XIRR reliability contracts and verifies calculator XIRR uses raw terminal value plus exact valuation date.

## D1a conclusion

D1d should **evolve**, not replace, the existing offline fixture/harness.

Preferred approach:

- create a versioned replay fixture (or upgrade via a v2 fixture) with fixed calculation-as-of;
- include at least one split-sensitive case, one dividend case, and FX variation while keeping fixture size reviewable;
- use frozen in-memory effective market/FX state with network forbidden;
- assert exact canonical output projection plus manifest digests;
- keep focused economic tests alongside the golden replay rather than overloading one fixture with every edge case.

# 8. Artifact / manifest boundary decision

## Proposed production manifest shape

Exact field names remain D1b work, but the approved direction is structurally:

- manifest/version + canonicalization versions;
- engine source commit;
- source records: SHA-256 + count + max id;
- runtime config: canonical identity/hash + resolved benchmark/base currency/policy diagnostics;
- effective market inputs: SHA-256 + symbol/row diagnostics + synthetic/realtime provenance summary;
- effective FX inputs: SHA-256 + currency/row diagnostics;
- calculation-as-of;
- run metadata such as calculated-at kept outside deterministic combined input identity;
- combined deterministic calculation-input digest derived only from versioned deterministic components.

The manifest must never contain free-form notes, user email, API keys, raw authentication data, or unnecessary vendor payloads.

## Storage decision

**Preferred D1e storage:** optional additive `PortfolioSnapshot.calculation_manifest` serialized in the existing opaque snapshot JSON.

Reasons:

- no D1 migration required;
- no Worker route/schema change required in principle;
- snapshot + evidence remain atomically associated;
- existing optional `benchmark_symbol` provides a compatibility pattern;
- latest ten snapshots already provide a limited historical evidence trail.

Before D1e, tests must explicitly prove:

- legacy snapshots without manifest validate/read normally;
- new snapshot manifest round-trips through model dump/validation;
- Worker upload/read accepts additive field and remains under size limit;
- frontend behavior is unchanged when the unknown field is present.

# 9. Proposed implementation sequence

## D1b — Pure deterministic manifest primitives

Implement without production runner integration:

1. versioned canonical JSON/hash utility;
2. normalized source transaction canonicalization/hash;
3. runtime config canonicalization/hash;
4. validated engine source-commit resolver;
5. manifest Pydantic models / deterministic combined input identity;
6. tests proving stable hashes, material-change sensitivity, excluded volatility and fail-closed invalid inputs.

**No D1/Worker change. No market provider abstraction.**

## D1c — Effective market/FX provenance extractor

Implement pure extraction from existing `MarketDataClient` state:

1. effective calculation market-input projection/hash;
2. FX projection/hash;
3. reuse transaction-calendar valuation provenance;
4. structured tracking for price-selection/realtime override provenance only where current metadata is otherwise lost;
5. network-free tests based on existing pure market invariants.

## D1d — Deterministic golden replay

1. introduce the narrow calculation-as-of/clock context required for determinism;
2. evolve the current mixed TW/US golden fixture;
3. prohibit network during replay;
4. assert authoritative snapshot projection, Daily-P&L ledger, TWR/XIRR metadata and manifest digests;
5. prove repeated replay byte/content identity for the deterministic projection.

## D1e — Smallest production integration

Only after D1b–D1d pass independently:

1. add optional `calculation_manifest` to `PortfolioSnapshot`;
2. construct it at the authoritative runner boundary after effective inputs are known;
3. associate it with the calculated snapshot before validation/upload;
4. preserve legacy snapshot/frontend compatibility;
5. production smoke only if runtime path changes materially.
